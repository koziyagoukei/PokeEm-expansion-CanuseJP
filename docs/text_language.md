# テキストの表示言語

## 基本仕様

この日本語向け基盤では、日本語フォントをデフォルトにしています。

| 文字列の先頭 | 表示モード |
| --- | --- |
| 指定なし | 日本語 |
| `{JPN}` | 日本語 |
| `{ENG}` | 英語 |
| `{AUTO}` | 続く文字・展開先を基に判定 |

```c
const u8 gText_Example[] = _("こんにちは");
const u8 gText_ExistingExample[] = _("{JPN}こんにちは");
const u8 gText_EnglishExample[] = _("{ENG}HELLO");
const u8 gText_MixedExample[] = _("こんにちは {ENG}HELLO{JPN} またね");
```

イベントスクリプトの `.string` でも同じ指定が使えます。

```asm
Example_Text_Greeting:
	.string "こんにちは\nげんきですか？$"

Example_Text_English:
	.string "{ENG}HELLO!$"
```

既存の `{JPN}` は有効なままです。独立して表示される会話・説明文などは、描画前後の比較を行ったうえで、不要な先頭指定を順次削除しています。文字列の途中の切り替えや、保存される名前の言語判定にも使う指定は保持します。

## 混在テキストと変数

`{ENG}` / `{JPN}` は、別の指定が現れるか、その文字列の描画が終わるまで有効です。英語部分を挿入した後に日本語へ戻す場合は `{JPN}` を付けます。

```c
const u8 gText_VariableExample[] = _("{STR_VAR_1}{JPN}を えらんだ！");
```

変数内に言語切り替えがあると、その切り替えは展開後の本文にも引き継がれます。変数の終端で、呼び出し元のモードへ自動的に戻る仕組みではありません。英語本文に日本語の名前を挿入する場合など、必要に応じて変数の後に `{ENG}` を指定してください。

`ConvertInternationalString()` が日本語名に付ける終端のモード指定は、デフォルト言語に戻すようにしています。従来と同じバッファ容量で、日本語名の後の本文だけが英語になってしまう問題を避けます。保存データの形式や言語IDは変更していません。

## 記号と自動判定

この変更はフォントの選択方法を変えるもので、文字コードの割り当てを変えるものではありません。`charmap.txt` とフォントPNGは変更していません。

- ひらがな・カタカナは、これまでどおりゲーム内の1バイト文字コードへ変換されます。
- 英語フォント固有の記号・アクセント文字を使う場合は、明示的に `{ENG}` を指定してください。同じバイトが日本語では仮名を表す場合があります。
- `EMOJI_XXXX` や拡張記号は通常のASCII文字とは別で、対応する拡張記号側のグリフを使います。
- ボタンアイコンは従来のアイコン画像を使います。
- 数字 `0`〜`9` は、日本語モード内でも対応する英語フォントのグリフと字幅を使います。数字の後の仮名は日本語モードのままです。
- `{AUTO}` はデフォルトへ戻す指定ではありません。次の文字などからモードを選ぶ既存の判定です。数字や記号から始まる日本語には、無指定または `{JPN}` を使ってください。

無指定の英語文字列も日本語モードで表示されます。英語モードの字幅を前提とする未翻訳テキスト、数値表示、特殊記号などは、必要に応じて個別に `{ENG}` を付けてください。すべての画面の表示幅を自動調整する変更ではありません。

### 数値と単位の表示

HP・PP・能力値・図鑑番号など、英語UIの狭い枠へ表示する数値全体には `{ENG}` を指定します。これにより、数字だけでなく、桁合わせ用の空白、`/`、`Lv`、小数点、`cm`・`kg` も英語側の字幅で揃います。`ConvertIntToDecimalStringN()` などの変換関数は、従来どおり数字だけを出力します。小さいバッファの容量を変えてしまうため、これらの関数へ一律に言語コードを追加しないでください。

```c
// gStringVar1など、制御コードを含む表示用バッファに組み立てる場合。
u8 *ptr = StringCopy(gStringVar1, COMPOUND_STRING("{ENG}"));
ConvertIntToDecimalStringN(ptr, value, STR_CONV_MODE_RIGHT_ALIGN, 3);
```

`.` と `。` は既存charmapではどちらも `0xAD` です。描画側から元の表記を区別できないため、日本語本文の句点は維持し、小数点やASCII記号を含む数値欄を `{ENG}` にします。数値を日本語本文へ連結する場合は、その後の本文を `{JPN}` で戻してください。

```c
const u8 gText_NumberWithUnitExample[] = _("{ENG}{STR_VAR_1}.{STR_VAR_2} kg{JPN}の ポケモン");
```

戦闘のLv100とPP、手持ちHP、ステータス値と技詳細、全国図鑑の4桁番号・寸法をmGBAで確認しています。図鑑詳細の名前位置は番号の実際の字幅から決め、番号が4桁になっても重ならないようにしています。

## 設定と実装

`include/config/text.h`:

```c
#define TEXT_JAPANESE_BY_DEFAULT TRUE
```

`FALSE` にすると、無指定の文字列を先頭の文字などで判定する従来方式に戻せます。`FALSE` は英語固定を意味しません。どちらの設定でも `{JPN}` / `{ENG}` / `{AUTO}` は使えます。

共通処理は `src/text.c` にあります。`IsJapaneseTextMode()` を描画開始と `GetStringWidth()` の両方で利用し、モード切り替え・変数・制御コードを考慮して幅を計算します。日本語の7px送りなど、既存のフォント設定は維持しています。

制御コードの引数に言語切り替えや終端と同じバイト値が含まれていても、通常の文字として誤解釈しないようにしています。

## 確認方法

```sh
python3 -m unittest discover -s tools/tests -p test_text_language_mode.py -v
python3 tools/check_jp_text.py
make -j4 --output-sync=target
```

回帰テストはホストCコンパイラを使い、実際の描画処理・幅テーブル・グリフ選択処理を実行します。VRAMへの書き込みなどのハードウェア部分は代替しているため、画面の見た目の確認は別途必要です。

ゲーム内では、接頭辞なしの会話、既存の `{JPN}` 付き会話、`{ENG}` の英語表示、主人公名・ニックネームの挿入、数字・記号、メニューの位置と改行を確認してください。

## 先頭指定の整理

最初の整理では、380ファイルの10,619件から先頭の `{JPN}` を削除しました。主な対象は、マップ会話、トレーナー会話、テレビ、マッチコール、技・特性・アイテム・図鑑の説明、および単独表示を確認したUIテキストです。本文、ラベル名、イベント命令、文章途中のモード指定は変更していません。

次の指定は一括削除の対象にしていません。

- 種族名・ニックネームなど、名前や言語情報としても扱われる文字列。特に `src/pokemon.c` には、ニックネーム先頭の `{JPN}` から言語IDを設定する処理があります。
- 他の文章へ連結したり、変数へ代入したりする共通部品。直前が英語モードの場合、先頭の `{JPN}` が必要です。
- 呼び出し元をまだ確認できていないラベル、先頭の空白を含む文字列、検証用エンコーダが未対応の表記。
- 連続する `.string` やCの隣接リテラルの途中にある `{JPN}`。物理的な行頭でも、表示する文字列全体の先頭とは限りません。

整理用ツールは、まず変更せずに一覧を出力します。

```sh
python3 tools/remove_redundant_jpn.py --report build/reports/jpn_prefixes/plan.json
```

反映にはホストCコンパイラ `cc` または `gcc` が必要です。WSLのリポジトリ内で実行してください。

```sh
python3 tools/remove_redundant_jpn.py --apply
python3 -m unittest discover -s tools/tests -p 'test_*jpn*.py' -v
python3 tools/check_jp_text.py
make -j4 --output-sync=target
```

`--apply` は、削除候補を既存charmapで符号化し、実際のC描画処理・字幅計算で省略前後を照合してから書き換えます。9種類のフォント、日本語・英語・混在の3種類の変数内容を比較し、不一致があれば反映を止めます。改行コードは保持し、先頭の指定だけを削除します。

判定結果と反映前のソースハッシュは `build/reports/jpn_prefixes/migration.json` に保存します。初回は10,619件を反映し、10,796件を保持しました。保持件数には、今後呼び出し元を確認すれば削除できる可能性があるものも含みます。レポートは生成物なのでGit管理しません。

`{AUTO}` への機械的な置換は行いません。たとえば `10%で まひ` に `{AUTO}` を付けると、先頭の数字から英語モードを選んでしまいます。今回の対象では補助指定の追加は不要でした。可変テキストを自動判定したい場合だけ個別に使い、その後の本文のモードも確認してください。

2バイトの指定を削除しても、ROMの縮小量は条件付きコンパイル・文字列共有・アラインメントで変わります。パディング済み `.gba` のファイルサイズは変わらない場合があります。

- mGBAで新しいROMを起動し、メニューとオダマキの会話を確認しました。タイトル、メニュー、会話の表示完了後の画面は整理前とピクセル単位で一致しました。表示途中は制御コードの削減によって文字送りの進行が異なるフレームがあります。
- mGBA上の9フォント比較画面でも、`{JPN}` あり・なしの描画結果が一致しました。
- `python3 tools/check_jp_text.py`、全111件のツール回帰テスト、`make -j4 --output-sync=target`、`git diff --check` が成功しました。
- 全マップ・戦闘・通信・既存セーブの全画面確認は未実施です。名前と連結部品の指定は、その互換性確認を別途行うまで残します。
