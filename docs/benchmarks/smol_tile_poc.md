# タイル重複排除とsmolの組み合わせ検証

## 結論

2026-10-25時点では、**本実装しないことを推奨します**。
既存smolを残したPC用PoCを作成し、ROMと一致する4,761画像で比較しました。
前面1,479画像では、画像内重複排除で8.75〜9.18%、共有辞書付きで最良でも10.77%増量しました。
本体だけでは小さくなりますが、番号列と管理情報を足すと現行smolに勝ちません。

ゲームの圧縮・展開処理、ヘッダ、Makefile、画像、パレット、ROMは変更していません。
Huffman移植、独自LZ77展開器、BIOS入口フック、既存画像の一括変換も行っていません。
追加物はPC用ツール、テスト、本資料、画像を含まない集計結果だけです。

## 1. 現行smolの処理

```text
PNG → gbagfx → 4bppのタイル列 → compresSmol → .4bpp.smol
```

`Makefile:537`以降に変換ルールがあります。`%.smol` は `compresSmol -w`、
`%.fastSmol` は `compresSmol -w ... false false false` を使います。
`src/data/graphics/pokemon.h` の前面は通常 `anim_front.png.4bpp.smol`、背面は `back.png.4bpp.smol` です。

`tools/compresSmol/compressAlgo.cpp` の主な入口は次の通りです。

- `processImage()` / `processImageData()`：1ファイルずつ独立に処理。
- `getShortCopies()`：u16単位の過去データ参照と繰り返しを検索。タイル境界に限定しない。
- 最小コピー長2〜15と複数モードを試し、ヘッダ・モデル込みの最小結果を選択。
- `fillCompressVec()`：命令列とリテラルをニブルに分け、必要に応じて差分化・tANS符号化。
- tANSは64状態。命令用・リテラル用の頻度表は各ストリームに保存され、画像間で学習・共有しない。
- `.fastSmol` は `BASE_ONLY`。tANSを省略し、ROM上の命令・リテラルを直接使う。
- `processImageFrames()` / CLIの `-fw` は未実装。別画像をまとめて共有する経路ではない。

アニメ前面PNGに複数フレームが入る場合は、それらを含む**同一ファイル内**の繰り返しも利用できます。
「同一タイルを利用していない」のではなく、既に一般的な一致列として圧縮しています。
一方、完全一致32バイトタイルを先に統合して番号列を出す処理や、任意の画像間辞書はありません。
通常のgbagfx変換も、タイル順を保って4bppへ変換し、sprite用の共有辞書を生成しません。

### 展開と既存の共有

`src/decompress.c` の `DecompressDataWithHeaderWram()` / `DecompressDataWithHeaderVram()` は、
ヘッダにより既存LZ77・smol・smolTMを振り分けます。
`SmolDecompressData()` はtANSを必要に応じて展開し、IWRAMへコピーした命令展開処理を使います。
`BASE_ONLY` は命令・リテラルの一時配列を確保しません。今回この高速経路は変更していません。

`LoadSpecialPokePicIsEgg()` は種族・性別・タマゴを解決した画像をWRAMへ展開します。
一般的な `LoadCompressedSpriteSheet()` も展開後に通常のsprite sheetとしてロードします。

既存の `smolTM` には**タイル番号のu16差分化＋コピー圧縮**があります。
これは画像のタイル本体を画像間で共有する機能ではありません。
マップの共通tilesetや、複数フォームが同じ画像ポインタを参照する再利用もありますが、
smolの圧縮モデル・辞書の自動共有とは別です。

## 2. F-compから参考にした部分

参照した実装は [`tools/fcomp.py`](https://github.com/pm-start/CFRU-JP-fcomp/blob/c71aa64e4947357846c1ba101ab9c0af3660ef1d/tools/fcomp.py) です。

- `split_tiles`：完全一致する32バイトをまとめ、元の順序を番号列にする。
- `body_of`：unique tile列＋1または2バイト幅の番号列を作る。
- `build_dictionary`：同一画像で何回出たかではなく、**何画像に出たか**を数え、2画像以上に出るタイルを優先。
- `lz_tokens`：辞書を画像本体の手前に置く仮想履歴として使い、LZ77参照から辞書を読めるようにする。

最後の辞書付きLZ77は、現行smolへ単に辞書を渡せば使えるものではありません。
現行 `processImageData()` に外部辞書引数はなく、現在の展開処理もその仮想履歴を前提にしません。
そのため本PoCのCでは、辞書参照を**明示的なタイルID**に置き換え、残るデータだけを既存smolへ渡しました。
F-compのLZ77自体の性能比較ではありません。Huffmanと全画像共通符号表は対象外です。

## 3. PoCと集計方法

追加ツール: `tools/smol_tile_poc.py`。元画像・元圧縮ファイル・ROMは読み取り専用です。

| 方式 | 圧縮するデータ |
| --- | --- |
| A | 元の4bppを既存smolで圧縮。現行圧縮ファイルおよびROMと完全一致も確認 |
| B split | unique tileをsmol、番号列も別のsmolで圧縮 |
| B combined | unique tile＋番号列を1つのsmolで圧縮 |
| C split | 共通辞書にあるタイルを除いたlocal unique tileと、共通/ローカルID列を別々にsmol圧縮 |
| C combined | Cのlocal unique tile＋ID列を1つのsmolで圧縮 |
| 補足tilemap | 番号列だけ既存 `compresSmolTilemap` に渡す。新しい差分圧縮器は作らない |

番号幅は1または2バイト。Cでは共通IDの後にローカルIDを割り当てるため、8KiB辞書の256タイルを
使い切った場合でも、ローカルタイルがあれば2バイト幅になります。
辞書は同じ種類の画像内で共有し、容量上限を8 / 16 / 32KiBで比較しました。
頻度の同率時はタイルバイト列で順序を固定し、再現性を確保しています。

### 必ず数えた容量

- 4バイト/画像の共通参照表：A/B/Cすべてに計上。
- B/C専用PC実験ヘッダ：20バイト/画像。
- 画像の圧縮本体、番号列、smol自身のヘッダ・頻度表・4バイト境界パディング。
- Cの共有辞書本体、16バイトの辞書管理情報と4バイトの辞書参照。
- 辞書をROMへrawで置く場合と、辞書自身もsmolで圧縮する場合の両方。

combinedの番号列は圧縮本体に含まれます。別途番号列0バイトという表示は、番号列を無料扱いした意味ではありません。
既存gSpeciesInfo等の全構造体を数えた「完成ROMサイズ」ではなく、同じ参照表を持つ比較バンドルの総容量です。
新規ローダのコード容量や、本実装で並行テーブルが必要になった場合の追加容量は未計上なので、なお楽観的な比較です。

`STP1` はPC実験だけの外側のヘッダです。**そのままゲームの展開関数に渡してはいけません。**
内側のsmolヘッダは変更せず、通常smolは既存CLIの `-d`、smolTMは既存ツール内の往復検算で確認します。
キャッシュ済みsmolも実際に再展開し、最後にタイルを並べ直して元の4bpp全体と比較します。

## 5. なぜ縮まないか・損益分岐点

前面の162,240タイルは画像内統合により90,421タイルになります。
rawでは2,298,208バイト減りますが、smol本体の差は1,583,876 → 1,558,124の25,752バイトだけです。
既にsmolがその繰り返しの多くを短いコピー命令にしているためです。
そこへ142,076バイトの圧縮indexと29,580バイトの画像ヘッダが加わり、逆転します。

前面Cの各設定は、辞書代を払う**前**から1画像平均で115バイト以上増えています。
今回の画像分布では、利用枚数を増やして辞書代を償却する損益分岐点はありません。
JSONには平均損益、辞書費、名前順prefixでの損益分岐点も記録しています。
他の画像集合でも必ず同じ結果になるという意味ではありません。

20バイトのヘッダを小さくするだけでも解決しません。
今回のC 32KiB splitで、仮にindexと全画像ヘッダを無料にしても、辞書・本体・共通参照表の合計は1,538,144バイトです。
この構成に限った理想上限でもAから51,648バイト、約3.25%の削減に留まります。
本格的な新方式の性能上限を示す数値ではありません。

## 6. RAM・速度・保守

### RAM見積もり

既存ヘッダの実値と `SmolDecompressData()` の確保式から算出しました。
これは必要バッファの見積もりであり、GBA上でのピークRAM実測ではありません。

```text
A: 元画像の出力R ＋ smol一時配列S
B: 出力R ＋ unique/index展開用W ＋ smol一時配列S
C・辞書raw: Bと同じ構成、辞書タイルはROM参照
C・辞書smol: 上記 ＋ 展開済み辞書Dを常駐
```

splitではuniqueとindex用の両方を確保し、呼び出すsmolの一時配列は大きい方をピークに数えます。
`BASE_ONLY` とsmolTMの一時配列は0、通常smolは `2*align2(symSize)+align2(loSize)` です。
辞書展開時だけのピークも比較しています。アロケータ管理域、共通IWRAMテーブル、スタック、
他の画面・spriteバッファは別途必要です。出力Rも通常の呼び出し元バッファを含みます。

| 前面・split | 最大バッファ合計 | Aからの画像ごとの最大追加 |
| --- | ---: | ---: |
| A | 7,548 | 0 |
| B | 11,632 | 4,084 |
| C・辞書ROM raw | 11,694 | 4,146 |
| C・8KiB辞書をsmol格納・RAM常駐 | 19,886 | 12,338 |
| C・16KiB辞書をsmol格納・RAM常駐 | 28,078 | 20,530 |
| C・32KiB辞書をsmol格納・RAM常駐 | 44,462 | 36,914 |

`HEAP_SIZE = 0x1C500` は総計113.25KiBであり、現在の空きヒープを意味しません。
32KiB辞書の常駐はその総ヒープの約28%に相当します。容量削減がない状態で負うには大きなコストです。

### 速度とVRAM

既存smol/tANSを内側の展開にそのまま使うことはできますが、復元は「smolを呼ぶだけ」では終わりません。
splitは通常2回の展開とタイル並べ直し、combinedも一時本体の展開と並べ直しが必要です。
OBJの大きなspriteは連続したタイル配置を使うため、BGのように任意のタイル番号列を渡すだけにはできません。
従来の連続4bppシートへ復元し、`LoadSpriteSheet()` 等へ渡す必要があります。

WRAM経由なら追加バッファとコピー、VRAM直接出力なら半wordアクセス・転送順序を守る専用経路が必要です。
既存の一括展開・転送より複雑になり、小さな画像では呼び出しやtable構築の固定費も増えると予想します。
**GBAの実行サイクル・フレーム時間は測定していないため、何倍遅いかは断定しません。**

### PCビルド時間

前面1,479画像を新しいキャッシュで、A/B/C32KiB・splitの順に4 workerで測った参考値です。
既存ツールの圧縮とPC往復検算を含み、通常の増分makeや純粋なエンコーダCPU時間とは異なります。

| 処理 | 時間 |
| --- | ---: |
| A | 17.38秒 |
| B split | 22.27秒、別途タイル計画0.04秒 |
| C 32KiB split | 22.40秒、別途辞書・タイル計画0.20秒 |
| A/B/Cを通した計測 | 62.34秒 |

全4,761画像・複数辞書・両レイアウトの最終再検算は186.70秒で、キャッシュありです。
通常smolストリームだけでも51,382種を扱っています。実行機の負荷や保存先で時間は変わります。

### 変更と保守の負担

- Bは原則として変更画像だけを再生成できる。
- Cは画像追加・編集で頻度と辞書IDの順序が変わり、同じ辞書を使う画像群のindex再生成が必要になり得る。
- 辞書を固定すれば更新範囲を抑えられるが、頻度最適化を保てず、辞書版の管理も必要になる。
- 表・本体・indexの不整合、範囲外ID、辞書寿命、同時読み込み、ヒープ不足という新たな故障要因が増える。
- 既存smolヘッダのままでは外側のタイル構造を識別できないため、専用の呼び出し元・sidecar管理も必要。

## 7. 実装判断と、将来試す場合の最小案

今回は、数百KiB削減や10〜20%改善という基準を満たさず、むしろ増量してRAM・処理も増えるため見送ります。
「F-compそのものが悪い」「外部辞書を持つ全方式が無効」という結論ではありません。
**指定された前処理を、現行smolを変更せずに合わせた今回のタイル参照方式**についての判断です。

将来、別の同系画像群で十分な改善が実測できた場合だけ、次の順で検討します。

1. その小さな画像群だけで辞書を固定し、既存smolストリームを保持したsidecar情報を生成。
2. `src/tiled_smol.c` 等に専用WRAM復元関数を追加し、内側は既存 `DecompressDataWithHeaderWram()` を呼ぶ。
3. まず1つの専用画面だけをopt-in。旧画像・既存ローダは維持し、画像サイズ照会・直接参照箇所を先に監査。
4. GBA側でピークヒープ・最大ロード時間・VRAM転送・複数同時表示を実測する。
5. 専用関数・参照表・コード追加まで含む最終ROM差が十分に有利な場合だけ、対象を拡大。

既存ヘッダへ勝手に新modeを追加したり、全画像ポインタをPoCの外側ヘッダへ置換したりする案ではありません。
この設計案は未実装であり、現時点で通常ビルドへ接続する予定はありません。

元のROM・ELFは検証前後のSHA-256一致を確認しました。
ゲーム側は未変更のため通常ROMの再ビルドは行わず、PCツールのビルド確認・圧縮・復元検算を実施しています。
実機・エミュレータで新しい読み込み方式を動かす試験は行っていません。

リポジトリルートで、通常ビルドの `pokeemerald.gba` / `.elf` と4bpp生成物がある状態で実行します。
Linux/WSLの既存ツールを使用します。圧縮・検算キャッシュはROMや元画像とは別です。

```sh
make -C tools/compresSmol
python3 tools/smol_tile_poc.py --inventory-only
python3 tools/smol_tile_poc.py --cache-dir /tmp/pokeemerald-smol-tile-cache --workers 4
python3 tools/smol_tile_poc.py --groups front --layouts tilemap \
    --output build/reports/smol_tile_poc/tilemap --cache-dir /tmp/pokeemerald-smol-tile-cache
python3 tools/smol_tile_poc.py --groups front --limit 128 --fast \
    --output build/reports/smol_tile_poc/fast --cache-dir /tmp/pokeemerald-smol-tile-cache
python3 -m unittest discover -s tools/tests -p test_smol_tile_poc.py -v
```

smolTM補足比較は少なくとも8タイルある画像に限定します。通常のsprite圧縮全体をsmolTMに置き換えるものではありません。
`--baseline-only` でAだけの計測、`--dictionary-kib` で辞書上限、`--limit` で決定的な等間隔サンプルを指定できます。
既存の `build/` 除外を使うため、生成物用にgitignoreの範囲は拡大していません。
