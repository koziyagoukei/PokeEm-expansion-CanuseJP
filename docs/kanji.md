# 漢字の自動検出とフォント生成

## 使い方

ゲーム用の表示文字列にUTF-8で漢字を書き、通常どおりビルドします。文章の漢字変換や、翻訳文の自動書き換えは行いません。

```c
const u8 gText_Example[] = _("今日は良い天気ですね。");
```

```asm
Example_Text::
    .string "{KANJI}今日は良い天気ですね。$"
```

```sh
make -j4 --output-sync=target
```

この例では「今・日・良・天・気」を検出し、新しい字のIDを台帳へ追記し、使用字のフォントを生成します。日本語モードがデフォルトなら `{KANJI}` は必須ではありません。`{JPN}` / `{ENG}` / `{AUTO}` / `{KANJI}` と既存のプレースホルダーも使えます。

**プレイヤー名、ニックネーム、保存・通信に入る名前や定型文には漢字を使わないでください。** ビルド時検査は既知の経路を検査しますが、任意のCコードのデータフローを証明する仕組みではありません。

## 導入

通常のビルド環境とPython 3の標準ライブラリを使用します。通常ビルドでフォントのダウンロード、TTFの配置、PillowやfontToolsの導入は不要です。リポジトリのアトラスから必要な字だけを生成します。BPEJのフォント素材を追加する仕組みではありません。

公式配布の `KH-Dot-Kodenmachou-12.ttf` から生成した12×12pxのアトラスに、漢字6,356字と「々・〆・〇」の計6,359字を収録しています。収録範囲外の字は、ファイル名・行番号・Unicode番号を示してビルドを停止します。欠字を他のフォントで代用したり無視したりはしません。

## 検出範囲

| 対象 | 検出するもの |
| --- | --- |
| `src/`、`include/` のCソース・ヘッダー・C用 `.inc` | `_`、`__`、`J_`、`J__`、`COMPOUND_STRING`、`J_COMPOUND_STRING` の引数 |
| 上記へ引数を渡す関数形式マクロ | `#define` を追跡。`ITEM_NAME`、`MESSAGE`、`EXTRA_NPC` など |
| `data/` などの `.inc` / `.s` | `.string` / `.braille` のリテラル |
| `test/` | 同様にIDを登録。テストだけで使う字のグリフは通常ROMに入れない |

コメント、識別子、include先、素のC文字列、README、docs、ライセンスは対象外です。`.pory` は現在 `workspace/templates/` のテンプレートだけで、Makefileのコンパイル対象ではないため走査しません。Poryscriptを使う場合は、ビルド対象の `.inc` を生成してからmakeしてください。

Cの完全なマクロ展開・条件コンパイル・リンカGCは再現しません。無効な条件分岐の文字列も含まれる場合があります。対象は「実行時に必ず参照される字」ではなく「走査対象の表示文字列に記述された字」です。特殊なマクロ展開で検出できなかった文字は、ビルド用charmapに含めないことで後続のpreprocでもエラーにします。過去に登録済みの字でも、見逃しを空白表示として通しません。

`.braille` の検出は点字描画への漢字対応を意味しません。`FONT_BOLD`、点字、一部の独自UIの描画は今回の検証対象外です。

## ID台帳

ルートの `charmap_kanji.txt` が永続ID台帳で、`charmap.txt` が `.include` で読み込みます。**生成物ではなくソースとしてGit管理し、文章の変更と一緒に台帳への追加も管理してください。**

- 既存25字の `FC 1F 01`〜`FC 1F 19` は固定です。失われたり変更されたりするとエラーになります。
- 新出字はUnicode番号順で末尾へ追記します。走査順に依存せず、過去のIDは変更しません。
- 文章から消えた字のIDを削除・再利用しません。再登場したときは元のIDを使います。
- 台帳がなくなった場合は再採番せず停止します。Gitから復元してください。
- 別ブランチで同じIDを別の字へ振った場合は、マージ時に調整してください。字・IDの重複やbase charmapとの衝突はエラーになります。

符号化は1字3バイト。`FC 1F xx`〜`FC 27 xx` の9バンク、各 `xx=01..F6`、最大 **2,214字** です。`F7..FF` は制御値との衝突を避けるため使いません。`{KANJI}` は従来どおり `FC 1E` で日本語モードを指定します。新バンクはこのフォーク専用であり、upstreamが `0x20`〜`0x27` を使う場合は統合時に衝突確認が必要です。

## 生成物と依存関係

| パス | 役割 |
| --- | --- |
| `graphics/fonts/kanji/koden12_atlas.png` / `.txt` | 全収録字の編集用アトラス。全体をROMへ組み込まない |
| `charmap_kanji.txt` | 永続ID台帳。手動で再採番・削除しない |
| `build/generated/kanji/kanji_glyphs.fwjpnfont` | 使用字の2bppグリフ |
| `build/generated/kanji/kanji_slots.bin` | 永続IDから現在のグリフ位置への対応表 |
| `build/generated/kanji/charmap.txt` | 今回検出した字だけを含む、符号化用のcharmap |
| `build/generated/kanji/kanji_report.txt` | 文字数・容量・追加字等 |
| `build/generated/kanji/kanji.ok` | 検査・生成成功のstamp |

Makefileの `generated` で、他の自動生成ソースができた後に `tools/kanji/kanji_gen.py update` が走り、文字列符号化前に完了します。毎回の走査でソース削除や欠損した生成物も検知します。charmap・台帳の変更時は文字列符号化に依存するオブジェクトも再ビルドします。

字形と索引の内容が同じなら更新日時を維持します。台帳更新はロックで直列化し、検査・字形生成が失敗した場合は新規IDを書きません。個別のファイルは一時ファイル経由で置換します。ディスク書き込み中に止まった場合もビルドは続行せず、次回の生成で修復します。同じ場所で `make clean` と別のmakeを同時実行する運用には対応しません。

`make clean` は生成物を削除しますが台帳・アトラスは残り、次回も同じIDで生成します。`build/` 以下、完成ROM、baseromはコミットしないでください。

## 字形と容量

文字本体は12×12px、文字送り12pxです。影は生成時に右下1pxへ付け、枠外を切ります。既存かなの影とは完全一致しません。既存25字は、以前の `graphics/fonts/kanji_koden12.png` とのグリフバイト・ピクセル互換テストがあります。このPNGは比較基準として保持しています。

グリフは1字64バイト、8字単位で512バイトに配置し、空白グリフと余白を含みます。対応表は登録済み最大IDまで1項目2バイトです。字が文章から消えるとグリフは外れますが、台帳と対応表の項目は残ります。8字単位の余白があるので1字追加のたびにROMが64バイト増えるわけではありません。文章の符号化長・コード配置・アラインメントも変わるため、ROM全体はELFの `__rom_end` で比較してください。

かな・英字の最適化や1bpp化は行っていません。1bitアトラスは編集用の文字本体で、実行時のグリフは従来と同じ2bppです。

## 保存・通信データ検査

生成時に `tools/kanji/save_link_checks.py` が既知のデータを検査し、違反時はROMビルド前に停止します。長さは表示文字数ではなく、制御コードを含む**符号化後のバイト数**で、終端を除いたバッファ容量と照合します。

| 対象 | 主な保存・通信経路 |
| --- | --- |
| 種族名、タマゴ・ヌケニン名 | 既定ニックネーム |
| ゲーム内交換の名前・OT | ポケモン、メール送信者、交換 |
| トレーナー・パートナー・施設の名前 | OT、録画、インタビュー、TV、レコード交換 |
| トレーナーヒル・弟子・コンテストの名前 | 手持ち、勝者記録、TV、レコード交換 |
| 追加コンテストNPCマクロ | 各保存バッファに対応する名前引数 |
| プリセット主人公・クイックスタート名 | セーブの主人公・ライバル名、通信名 |
| ボックス既定名 | 数字2桁の余地を引いた名前バッファ |
| ユニオンチャット定型文 | 登録テキストの保存・送信 |
| 語り部・ワルダ合言葉・トレーダー・ファンクラブ名 | セーブ・通信・レコード交換 |

対応規則では、漢字コード、動的プレースホルダー、未知の文字・引数、長さを解決できない初期化をエラーにします。必須規則が1件も見つからない場合も停止し、ファイル移動等で検査が消えることを防ぎます。

**限界:** 任意の新しい関数、ポインタ経由のコピー、別マクロによる参照、外部入力までの全データフローは証明しません。新しい保存・通信経路を作るときは検査規則とテストを追加してください。検査に通ったから任意の文章を名前バッファへコピーしてよい、という保証ではありません。`StringCopyN` 等は今もバイト数で切るため、固定長バッファへ文章を移す箇所は個別監査が必要です。

## 実測結果と回帰確認

2026-10-27、Ubuntu / GNU Arm GCC 14.2.1、通常の `make -j4 --output-sync=target` で測定しました。元の文章に試験文字を加える作業は隔離した作業ツリーで行い、配布する文章や台帳には残していません。

| ケース | 台帳の登録数 | 使用グリフ数 | グリフ容量 | 索引容量 | ROM実使用領域 | 25字時との差 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 既存25字 | 25 | 25 | 2,048 | 52 | 26,487,036 | 0 |
| 「天」を追加 | 26 | 26 | 2,048 | 54 | 26,487,044 | +8 |
| 「今日天気良」の5字を追加 | 30 | 30 | 2,048 | 62 | 26,487,076 | +40 |
| さらに240字を追加、2バンク目を使用 | 270 | 270 | 17,408 | 542 | 26,502,900 | +15,864 |
| 追加245字を文章から削除 | 270 | 25 | 2,048 | 542 | 26,487,516 | +480 |

容量はすべてバイトです。1字・5字の試験は情報ビューアの本文へ追加したものです。270字の試験は符号化用の表示文字列を追加した生成・リンク確認で、ゲーム上の全270字の目視確認ではありません。本文やアラインメントも変わるので、差分は「漢字1字あたりの固定増分」ではありません。

最終25字ROMの `__rom_end` は `0x099428FC` で、`0x08000000` を引いた実使用量が26,487,036バイトです。以前採用した25字試作の26,486,732バイトに対して、今回のバンク・索引等を含む正味増分は **304バイト**。以前の未参照FRLGフォント整理による削減33,656バイトを変更したわけではなく、今回の機能分が別途増えています。EWRAMは226,840バイト、IWRAMは28,576バイトで、今回の漢字追加試験による増加はありません。

再測定は次のシンボルを確認し、本文・生成物・ビルド設定を揃えて比較します。`.gba` のパディング後サイズは使いません。

```sh
arm-none-eabi-nm -S --defined-only pokeemerald.elf | grep -E '(__rom_end|sKanjiGlyphs|sKanjiGlyphSlots)$'
```

確認結果:

- 配布対象の回帰テスト153件成功。既存25字のグリフバイト一致、混在・フォント切替・幅と描画送りの一致、プレースホルダー、制御コード除去・比較・大文字変換を含みます。描画側のテストはホスト実行で、ハードウェアI/Oとグリフ展開の入出力はスタブです。
- 追加、重複、ソース削除、走査順の変更、欠字、容量超過、台帳衝突、制御コード衝突、出力欠損、書き込み失敗を検査しました。並行した生成2プロセスでもIDが重複しません。
- 名前用データに漢字と上限超過文字列を加え、通常のmakeが生成段階で停止することを確認しました。拒否された更新では台帳・既存グリフを変更しません。
- 変更なしの再makeで、台帳・グリフ・索引と `text.o` / `ultra_help.o` の内容・更新日時が変わらないことを確認しました。毎回の走査・データ検査自体は実行します。
- `python3 tools/check_jp_text.py`、通常ビルド、隔離作業ツリーでの `make clean` 後の並列ビルドが成功しました。clean前後で永続台帳のハッシュは一致し、生成物は消去・再生成されました。

最終のクリーンビルドでは、WSL上で既存の `gbagfx` の起動が一度 `Invalid argument` で停止しました。同じ画像変換コマンドは単体再実行で成功し、その後のmakeも上記と同じROM実使用量で完了しました。この切り分けのための画像や音源処理のコード変更は行っていません。

各画面の最終ROMでの見た目、実機性能、通信プレイの実動作は今回未確認です。画面の目視確認は利用者側で行う前提です。バイト数で切る従来APIを漢字対応へ変更してはいないため、名前以外でも独自の固定長コピーを追加するときは監査してください。
