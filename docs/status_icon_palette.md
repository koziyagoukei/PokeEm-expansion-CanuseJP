# 戦闘中の状態異常アイコンの色

## 症状とデータ上の問題

相手の状態が「どく」のままなのに、自分の状態を「ねむり」「やけど」「まひ」等へ変えると、相手のアイコン背景まで同じ色に変わる動画が報告されています。

HPボックスは同じOBJパレットを共有します。状態異常の色は、バトラー0から3に対してパレット内の12・13・14・15番に書き込まれます。そのため、画像の色番号もバトラーごとに分かれている必要があります。

調査時の `graphics/battle_interface/status.png` / `status2.png` / `status3.png` / `status4.png` は、すべて同じ色番号を使っていました。日本語の画像は8bitインデックスPNGで、状態色に12・28・44・60・76番を使用しています。4bpp変換では下位4bitが残るため、いずれも12番になります。変換後の4枚もすべて、状態色654ピクセルが12番でした。

前回追加した `CopyStatusIconToHealthbox()` の実行時補正は、今回調べた生成コードにも存在しました。しかし元の生成データは未分離のままでした。今回は実行時補正だけに依存せず、ビルド成果物の段階で正しい色番号に固定します。動画と同一のセーブ・エミュレータ状態を再現した検証とは区別してください。

## 変更内容

- `tools/build_healthbox_status.py` で既存の `gbagfx` を呼び出し、生成した4bppの状態色だけを12＋バトラー番号へ割り当てます。
- `graphics_file_rules.mk` の専用ルールを、状態異常アイコン4枚だけに適用します。ほかのPNGの変換方法は変えません。
- PNG本体、字形、配置、パレットの実際の色、状態異常の効果処理は変更しません。
- 実行時補正も、旧データ・カスタム画像に対する防御として残します。
- 変換失敗時には既存出力を上書きしません。追加のPythonライブラリは不要です。

| 生成物 | バトラー | 状態色の番号 |
|---|---:|---:|
| `graphics/battle_interface/status.4bpp` | 0 | 12 |
| `graphics/battle_interface/status2.4bpp` | 1 | 13 |
| `graphics/battle_interface/status3.4bpp` | 2 | 14 |
| `graphics/battle_interface/status4.4bpp` | 3 | 15 |

各ファイルは576バイトです。どく・まひ・ねむり・こおり・やけど・しもやけの6種類が、それぞれ24×8px・3タイルで並んでいます。文字や輪郭の色番号2・3は維持します。パレットの12〜15番以外は変換しません。

## 検証

リポジトリルートでビルド後、次のテストを実行します。

```sh
make -j4 --output-sync=target
python3 -m unittest discover -s tools/tests -p test_healthbox_status.py -v
python3 tools/check_jp_text.py
git diff --check
```

テストでは4枚×6種類の色番号、字形・輪郭の不変、片方の色変更がほかへ波及しないこと、異常な入力、変換失敗時の出力保護を確認します。ARMツールと生成ROMがある場合は、ELFの `gHealthboxElementsGfxTable` の位置から実際のROM内容も確認します。ROM中の4枚が生成物とバイト一致し、色番号12・13・14・15で分離されていることを検証します。ROM未生成等でこの検査がスキップされた場合は、ビルド後に再実行してください。

実機/エミュレータでは、相手をどくにしたまま自分の状態を順に変え、相手の色が変わらないことを確認してください。ダブルの4匹同時表示、交代、状態回復、デバッグメニューや手持ち画面からの復帰も確認対象です。
